It sends no chat messages and starts no processes. `catalogHealthy` is a catalog assessment; it does not prove live UI delivery or full history fidelity. Its `readiness` is `ready` only when the supporting watcher, hook, provider routing, files, and local authentication configuration are also verified; inspection failures remain unknown.

## Preserve the working design

- **Direction:** Codex is authoritative for project membership and catalog names. Mirror eligible projects and their non-archived chats into Paseo. Unassigned non-archived Desktop-originated top-level chats with no project home are mirrored into `Recents` workspaces grouped by normalized cwd; probe, background, parented, ephemeral, cwd-less, delegated-source, or non-Desktop rows are excluded and counted, never planned — while lineage-only forks (no parent/delegation markers) stay eligible. A native project id or local assignment naming nothing known defers instead of joining Recents or hiding. Native project counts exclude the internal Recents scope. Live conversation turns can travel in either direction through the shared backend; project management is not a two-way merge.
- **Placement (umbrella mode, flag off — pre-migration legacy behavior):** The Paseo `Codex` container holds a workspace for each original project working directory. Keep each chat's real `cwd`; the container directory is only a grouping anchor. Projects with several working directories can have several workspaces. Standalone chats keep their exact real `cwd`, config, and history under `Recents` (one workspace, or `Recents · directory` per distinct cwd); a missing folder defers without hiding an already-managed row, and moves between project and Recents scopes preserve the existing agent identity.
- **Placement (flat mode, flag on, load receipt active):** one top-level Paseo project per child working directory (an empty child from its project root); hetero-cwd members admitted only by the narrow hook pair; unmapped rows homed by old-workspace reverse map. Unrelated, `Recents`, and example groups are untouched. Later chats for EXISTING mapped units join their unit. With the bidir feature flag OFF, entirely new future projects are NOT auto-created (unit set frozen); with the flag ON, new future projects enter the separate dynamic bidirUnits roster while the original 16 stay frozen. Removing the flag after an active migration does NOT restore the prior umbrella — never blind-remap or replay activation; reversal needs a new scoped review using private backups. Details: [references/workspace-layout.md](references/workspace-layout.md).
- **Creation (bidirectional, COMPLETE for creation-only scope):** a new Codex project gets its own top-level Paseo project/workspace and vice versa, each side keeping its own chats; no deletion/rename propagation; first-time folders need the user's standard Codex folder-trust action (only the pinned Store release is proven — newer versions defer for review). Details: [references/project-creation.md](references/project-creation.md). The closed flat migration stays closed; its unit-set freeze is untouched.
- **Removal (bidirectional, forward converged once):** newer removal request handled separately in [references/project-removal.md](references/project-removal.md); new 4 installed + support unchanged, flag ON; owner UI test converged once (53m33 on ORIGINAL 7, timing unresolved), reverse BLOCKED. Stage success: 4 updated + 3 unchanged (all-11 backup verified), 3 OFF + 3 ON healthy natural passes observed, 164/164, dup 0. Creation above stays COMPLETE; broad repair stays STOPPED.
- **Identity:** Import the original Codex handle. The Paseo record's `persistence.sessionId` must equal the original thread handle, and an existing record must retain its Paseo agent identity. Do not fork chats or synthesize copies of their history.
- **Lazy loading:** Catalog sync registers stored handles. Resume a thread only when it is opened or deliberately tested. Enumerating the sidebar must not load every chat, acquire all writers, or start all MCP runtimes.
- **Opened sessions only:** History recovery and refresh apply only to original handles currently loaded natively. A stored idle catalog row never loads a cold sidebar chat, and bulk initialization is never performed.
- **Paged history with real budgets:** The absolute restore deadline starts before initialize and covers every resume and paged read, bounded by the overall reconnect deadline (a socket opening past it never starts a restore); remaining time flows into each RPC, and no new step begins on expiry. Live reads, catch-up retries, and verification carry their own time/page caps plus a UTF-8 byte cap (multibyte text counts fully). Reaching a bound is reported, never silent: the adapter records an incomplete history and retries it on the live connection with a bounded policy (5 × 15s), and the worker pass counts unvisited sessions instead of skipping them quietly. Worker connects are bounded twice (SDK/handshake timeouts plus a race that closes only the loser — never the winner), a timed-out refresh closes both connections and aborts the pass, and catalog enumeration incompleteness is reported explicitly.
- **Incomplete is pending, never healthy:** An adapter whose catch-up failed tracks the gap per chat (in-memory only) and exposes only aggregate counts. A reconnecting adapter defers refresh until its own reconnect window settles (bounded adapter-side, then its heartbeat goes stale and classification resumes). Fresh subscribed gaps report `pendingHistory` / `waiting_for_history`. Retries-exhausted gaps resolve through one idle-verified refresh per 15-minute cooldown, at most 3 cycles per chat, then escalate to `needs_attention` (`worker-pass-gap` / `unresolved`) — never an endless loop, never a refresh during active/busy, never waiting forever.
- **Uncertain mutations quarantine:** Every refresh records a handle-hashed attempt marker in a private file BEFORE the mutation and clears it only on verified success (same id, same handle) or on read-only evidence of a NEW adapter spawned after the attempt — a same old adapter looking healthy again resolves nothing. Any failure past the write point (budget expiry, SDK timeouts, closed connections, post-refresh fetch failure, identity mismatch) retains the marker, so no follow-up refresh issues for that handle until re-observed; repeated observation failures escalate instead of waiting forever. Closing a socket cannot cancel accepted server-side work; the quarantine, not the close, prevents duplicates. Cleanup paths consume async close failures within a bound so they can never kill the loop, and a failed rpc initialize terminates its owned socket.
- **One watch worker:** The task mutex lives in the parent shell, so a restarted task orphans the node child; the worker therefore owns its role with a nonce-fenced heartbeat file. A verified live owner is never stolen regardless of heartbeat age (bounded passes outlast freshness windows; age alone never proves death — verified 2026-10-05 after a stale-heartbeat steal was removed); takeover needs a dead/foreign process, or an unverifiable process whose heartbeat is ALSO past the takeover window; claims resolve by write-then-reread nonce comparison; every status publish and every mutation re-verifies, and losers step down silently without clobbering status (proven with real simultaneous starter processes).
- **In-progress stream reconciliation:** The installed timeline merges adjacent same-turn text rows by concatenation and reconciles a completion against buffered streamed text — so a delta lost to an outage would corrupt the visible text if post-gap deltas were forwarded. The bridge mirrors per-item streamed prefixes: on a gap it synthesizes the authoritative missing segment from the saved snapshot exactly once, then withholds ambiguous post-gap deltas until the authoritative completion reconciles the exact remainder (reasoning streams use the same principle). From the moment a catch-up fails, the whole thread freezes (including not-yet-seen item IDs); completions still flow against the safe prefix, and a contradictory snapshot records an integrity gap rather than clearing silently. Withholding clears on item/turn completion and unsubscribe. A reconnect therefore briefly pauses live text growth for the affected item instead of corrupting it.
- **Reviewed-source builds:** Heartbeats carry a build signature hashed from the adapter source at spawn. The worker and inspector recompute the expected signature from disk every pass/run. Only idle opened sessions are upgraded to the reviewed build; an active reply keeps its serving adapter until idle.
- **No replay:** Reconnect and resume reattach subscriptions and replay saved UI items; model turns (`turn/start`, `turn/steer`, `thread/start`, `thread/fork`) are never resent. Paged history reads retry; anything else interrupted is reported once. Streaming reconciliation is proven end-to-end through the installed timeline store (lost middle delta, reasoning gaps, terminal replays); live-retry replays never suppress later live deltas.
- **Redacted errors, substantive cards:** Public status carries only whitelisted error stage/kind labels — never raw messages, handles, URLs, or credentials. History comparison verifies substantive question/option content (titles, labels, message text), never transient call/item IDs; missing actual content fails the check, and full-timeline paging (not a newest tail sample) backs every claim.
- **Async-question resolution sync:** Native history carries no answer-resolution field, but Desktop embeds canonical correlation in its structured user text: a `<send_user_message_question_reply>` wrapper around JSON entries pairing `[tool name, native async item id, zero-based index]` with the answer string. (Plain answers are ordinary user messages; dismissals send nothing at all.) A question answered in the other frontend stays pending locally until reconciled. On the Paseo side, TWO formats resolve with the same event pair a local answer emits: exact Paseo title blocks (`Answers to your questions:`) match ONE pending question whose FULL ordered title sequence exactly equals the block sequence (superset, subset, and reordered blocks never match on the live, late-proof, or saved-sweep paths), and Desktop canonical packets resolve ONLY their original records by exact native identity with index-ordered answers (complete groups only; malformed, partial, unknown, or duplicate-index groups stay pending) — live order-checked against redelivery, chronological native proof when items arrive late, and across history resync anchored on exact native item/call identity for title blocks (a lone assistant prose mention is not occurrence proof) and on exact item identity for canonical replies even without a projected call row. Ambiguous repeats, partial answers, free text, embedded packet snippets, and unrelated messages (even title mentions) never resolve anything. Redelivered answer notifications never resolve newer instances. A duplicate answer submit arriving through this bridge is refused at the transport instead of launching a second model turn (on turn/steer and turn/start: Paseo title submits blocked by native title answers including observed canonical ones; canonical-format submits accepted here blocked by exact answered item identity so a repeat for an old id stays refused while a new same-title id stays allowed). Scope honesty: Desktop's own channel goes gateway /desktop straight to native and bypasses this adapter, so the proven direction is a Desktop-first answer followed by a stale bridge-side submit (refused) - direct Desktop submissions are not guarded here and Desktop-side clearing plus live two-composer UI remain unverified: per-thread serialization with in-flight tracking (released on completion, definite rejection, loss, turn end, unsubscribe, and re-ask supersession — never reserved forever), ask/answer positions in item order, bounded authoritative verification that fails closed with an actionable error, and a bounded per-submit queue deadline. True cross-client simultaneity has no adapter-side atomic primitive and stays documented; sequential double-sends decide deterministically. A re-asked identical question stays answerable, and an already-resolved submit acknowledges idempotently without steering. Dismissals from the other side cannot sync (no protocol signal — stated, not invented), Desktop-side clearing is Desktop-internal and unverified.
- **Busy chats:** Defer placement, rename, hiding, daemon replacement, and backend restart when an affected chat is replying. Recheck idle state and backend generation immediately before an intentional restart.
- **Recovery:** Restore connections after a backend exit without replaying an interrupted user turn. Verification from an earlier backend generation is stale.
- **Privacy:** Keep settings, tokens, auth files, private inventories, session handles, raw transcripts, and logs outside the skill. Share only technical summaries and aggregate results.
