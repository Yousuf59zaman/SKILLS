# Shared backend, launch routing, and live delivery

## Installed architecture

```text
Codex Desktop -> local gateway /desktop -> one native Codex app-server
Paseo daemon -> stdio-bridge.mjs -> local gateway /paseo -> same app-server
catalog watcher -> gateway /check + Paseo client -> local stored catalog
```

The verified native listener is `127.0.0.1:19457`; the gateway/status listener is `127.0.0.1:19458`. These describe this custom bridge version. Inspect the source if another installation uses different ports.

`service.mjs` launches the configured native executable with `app-server --listen ws://127.0.0.1:19457`, the intended Codex home, and supported capability-token arguments. `gateway.mjs` gives each frontend a separate native WebSocket connection to that same backend process. It is not one shared JSON-RPC request-ID namespace. Temporary check clients initialize independently.

The gateway accepts only known routes, rejects browser-origin requests, and validates local transport authentication. Its frontend connection uses Basic credentials; its upstream connection uses a Bearer capability token. Keep the credential local and the listeners on loopback. Do not print credential-bearing URLs or persist them in the skill.

`settings.json` supplies Node, native Codex, CLI root, both application executables, both home directories, status output, and a private token. App and npm updates can invalidate paths. Discover the current Appx installation, native package executable, Node binary, and Paseo package rather than hardcoding the source computer's versioned app directory.

## Provider adapter and subscription fixes

Paseo's Codex provider command invokes Node plus `stdio-bridge.mjs`. Non-`app-server` calls such as version/capability checks must still delegate to the native Codex executable. App-server calls bridge JSON lines to authenticated WebSocket transport, preserving requests, responses, and notifications.

Two details made the integration work:

1. **Paseo owns its subscription.** Track thread subscriptions on that adapter connection. Filter successful `thread/loaded/list` results to threads subscribed by that connection so Paseo does not assume a thread loaded by Desktop is already subscribed for Paseo. Add/remove subscription membership on successful start/resume/unsubscribe responses.
2. **An opened Desktop chat subscribes.** When the Desktop connection reads opened-chat history, the gateway attaches that same connection through `thread/resume` with `excludeTurns:true`. Recognize `thread/read` with `includeTurns:true`, timeline/items reads, and relevant turns reads. Do not trigger this for metadata-only sidebar reads. Consume the gateway's internal resume response so the frontend cannot confuse it with its own request.

Paseo hydrates persisted history separately. The adapter adds `excludeTurns:true` to resume requests when that field is absent, avoiding another large history payload. Preserve explicit caller choices and check the installed API supports these parameters.

An imported record or `connected` socket is insufficient: both frontend connections must complete initialize. Check `initialized.desktop` and `initialized.paseo`. Catalog polling can succeed with Desktop initialized while the Paseo live adapter is temporarily disconnected.

## Recovery and verification generations

The supervisor keeps the gateway alive across a native crash, increments the backend generation, closes old frontend connections, and lets clients reinitialize. Control protocol 2 distinguishes planned account reloads from unexpected exits: planned reloads increment their own counter and do not consume or erase the genuine crash budget. Three unexpected failures within 60 seconds still stop automatic recovery. An explicit guarded launcher can request one authenticated recovery cycle from the stopped failed state, with a one-minute recovery cooldown. Unknown occupied ports are refused. Do not remove these bounds or replay model turns.

Recovery does not resend model turns. A response interrupted by a crash requires checking saved state before any explicitly requested retry. Mark previous verification stale on a generation change.

The original target-history status requires a ready backend, both initialized frontends, target history verification, reconnect success, and `verifiedBackendGeneration` equal to the live generation. Its historical two-chat target is not the project catalog's expected scope. `catalog-status.json` has a separate generation and aggregate count check.

The inspection performed while creating this skill found both frontends initialized and `currentSyncVerified:false` in the separate saved target-chat report. The scheduled watcher was stopped, but a later timestamp check confirmed a fresh `active` catalog snapshot. The first inspector had reparsed a UTC DateTime as local time, falsely adding six hours to its age; the corrected inspector preserves the timestamp's timezone. The saved target-chat report does not prove current delivery is broken; fresh complete live verification was not established. Diagnose or test when requested instead of promoting a saved success flag.

## Always-on supervision and launcher reliability (2026-10-05)

`Ensure-Backend.ps1 -KeepAlive` (task `PaseoCodexSharedBackendStartup`: logon + indefinite 10-minute repetition + a real repeating time trigger) supervises the shared transport without opening frontends or sending turns: ready states only observe; failed/missing OWNED backends self-heal (controlled generation-bound recover on protocol 2 with proven-ready wait, legacy FailedOnly stop with exact identity proofs, or boot onto free ports) with at most 3 heals/hour and long backoff. A separate single-iteration recovery pulse (task `PaseoCodexBackendRecoveryPulse`, same triggers) shares the single-healer plus backend-start mutexes, so exactly one actor heals at a time. Foreign listeners, occupied ports, manual account operations, and live switch fences stay observe-only with a published `needs_attention` state (`backend-supervisor.private.json`); nothing foreign is ever killed or replaced. The healthy monitor holds NO startup lock while observing (short-scoped per-round acquisition only) — a second process can always acquire the backend-start mutex mid-observation. Manual `codex-app` keeps FORCE default (bounded interrupt, never replay); its operation lock waits boundedly (~30s) instead of failing at once, and both it and every healer/rollout consult the exact-identity switch fence (pid + start ticks + exe + JS command + nonce; live or unverifiable blocks, proven-dead adopts, absent clears). Auth switches run the exact npm node + JS entry with a 120s bound; a timeout fences (never kills) the exact child and reports uncertain. Catalog discovery wakes early on native thread births/archives via file watchers (Created-only on `rollout-*.jsonl`, debounced, single reconciliation, polling fallback); session moves/renames wake via `Renamed` on `*.jsonl`, and local-project/assignment/title metadata edits wake via `Changed` on the single `.codex-global-state.json` file. Streaming JSONL appends never wake (no `Changed` subscription on session files), so a live reply cannot storm the reconciler; a flood valve paces pathological rates and watcher errors degrade explicitly with polling intact. Server-side-only title changes still arrive via native listing on the next pass. The guarded send/question daemon updaters hold the shared account/startup lock only across fast re-proof plus the stop/ensure mutation itself (millisecond file writes for canonical worker state; bounded fast rechecks for daemon reloads) — all 90s idle observation and every pacing/backoff wait runs lock-free, so a second process (e.g. manual `codex-app`) can always acquire the operation lock mid-observation. Manual `codex-app` keeps FORCE default (bounded interrupt of running replies, never replay); background updaters stay idle-only and never force. There is no standing permanent 120s-wait rule: waits are per-pass overall budgets (`MaxWaitSeconds` + 30s cleanup allowance), never an indefinite block.

## Account-switch failure repair

The old supervisor counted the launcher killing its native child for account reload as a crash; rapid planned reloads could exhaust the three-exit limit, leaving a failed supervisor alive while `Ensure-Backend.ps1` refused it. `Open-Shared-Apps.ps1` also immediately rejected an existing frontend whose shared connection had not yet reinitialized. Source inspection and isolated reproduction established these defects; the historical user failure was recovered by a PC reboot, so its complete pre-reboot crash sequence is unavailable.

`Backend-Control.ps1` sends private authenticated POST requests to `/control/restart` or `/control/recover`; `gateway.mjs` registers them only for authenticated loopback requests without browser Origin. `service.mjs` validates the current generation and fresh idle proof, blocks new frontend turns, rechecks native activity, then performs a planned native reload. Failed-state recovery requires the old native process to be finished and its port free. `backend-lifecycle.mjs` maintains the genuine failure window and recovery cooldown. Control status exposes `controlProtocol:2`.

`account-idle.mjs` checks all loaded native statuses and all Paseo agent pages using the installed SDK's `page:{limit,cursor}` and `pageInfo.nextCursor/hasMore` shape. A busy reply produces exit code 2; unknown status produces exit code 1 and is never treated as idle. Missing, repeated, or inconsistent pagination fails closed.

An already running legacy supervisor loads new code only after replacement. The guarded replacement verifies generation, fresh idle proof, exact executable/command/process creation, parentage, and listener ownership. It stops the exact old supervisor before its native child to prevent a respawn race. A stopped failed legacy supervisor can be replaced only when no native child/listener remains. No broad Node or Codex shutdown is used.

`Update-Backend-WhenIdle.ps1` provides a singleton hidden one-time deployment that waits up to 15 minutes for idle, serializes with manual switches, and performs that guarded replacement. It never stops Desktop or switches accounts. Read the aggregate `backend-upgrade.private.json` marker and live control protocol to distinguish waiting, active, timeout, and needs-attention results. A normal guarded `codex-app` also performs the legacy replacement when necessary.

The existing `codex-multi-auth-app-setup` installer now preserves an installed shared launcher instead of overwriting it with its standalone template. Keep that guard when updating setup code.

Validation used an isolated supervisor and fake native server on separate test ports: five rapid planned reloads stayed healthy; three real fixture crashes tripped the limit; authenticated recovery restored service; Origin/wrong credentials, stale generation, and a newly active reply were refused; no model turn was replayed. PowerShell fixtures cover startup/reconnect, positional account switching, busy waits, migration identity checks, and deferred deployment on Windows PowerShell and PowerShell 7. These fixtures did not switch live accounts or prove current two-composer live delivery.

## History-refresh failure repair

Symptom: Paseo shows "Couldn't refresh agent history" for a chat that advanced in Codex Desktop, while the catalog stays healthy. Root causes seen: (a) the chat's stdio adapter lost its subscription or heartbeat after a backend reload and never reattached; (b) a transient `waiting_for_connection` in the recovery worker during gateway restart.

`history-recovery.mjs` (scheduled task `PaseoCodexHistoryRecovery`, `--watch` loop, plus one-shot runs) reconciles this without touching turns: for each non-archived, non-closed Paseo `codex` agent whose original handle is currently loaded natively, it resolves the adapter state from private heartbeat records only. `healthy` requires a fresh (≤30s) alive non-closed version-4 record in `ready` state whose build signature matches the bridge source recomputed that pass and whose gap counters are zero — ready is required, because a reconnecting adapter may still be replaying history; refresh waits out its own reconnect window (`deferredReconnect` / `waiting_for_reconnect`, bounded adapter-side before the heartbeat goes stale and classification resumes). A fresh subscribed record with an active gap is `pending-history`; one whose live retries are exhausted is `exhausted-history`. Only an idle Paseo agent with an idle native thread, unchanged identity, and unchanged backend generation gets `refreshAgent` (same agent id and original handle preserved); anything busy, unknown, or changed is deferred, never replayed. Exhausted gaps resolve through one idle-verified refresh per 15-minute cooldown keyed by handle hash in a private file, at most 3 cycles, then escalate to `needs_attention` (`worker-pass-gap` / `unresolved`); the watch role additionally never leaves zero workers (verified-alive owners keep it at any heartbeat age, nonce fencing resolves starters, losers step down silently) — never an endless loop, never a refresh during active/busy. Each pass also prunes heartbeat records that are unreadable, closed, older than 30s, or whose process is gone; fresh alive records are never pruned. A pass is bounded (~120s plus bounded connects): every awaited operation races the pass deadline, native RPCs additionally receive the remaining time where supported, catalog-enumeration shortfall is flagged `enumerationIncomplete` with the remainder
`unvisited`, and a timed-out refresh closes both connections and aborts the pass. Closing a socket cannot cancel server-side work already accepted, so a handle-hashed uncertain record (private file, written before the mutation, cleared only on verified success or read-only evidence of a NEW adapter spawned after the attempt — a same old adapter looking healthy resolves nothing) quarantines the handle against any follow-up refresh until re-observed; repeated observation failures escalate, and any post-write failure (SDK timeouts, closed connections, post-refresh fetch failure, identity mismatch) retains the record. Async close failures are consumed within a bound so cleanup can never kill the loop, and a failed rpc initialize terminates its owned socket. Connects use SDK/handshake timeouts plus a race that closes only the loser — the closer must attach after the race is lost, never before, or it kills the winner too. The status file (version 4) reports `checked/upgraded/deferredBusy/deferredReconnect/healthy/pendingHistory/exhaustedGaps/gapRecovered/unresolvedGaps/quarantined/failed/unvisited` plus `status` (`active`, `waiting_for_idle`, `waiting_for_reconnect`, `waiting_for_history`, `waiting_for_backend`, `waiting_for_connection`, `needs_attention`) and whitelisted `errorStage`/`errorKind` labels — raw error text, handles, URLs, and credentials are never persisted. A stale status file (no fresh pass for ~90s) means the watch worker exited or orphaned duplicates are racing: the task's Running flag alone is not health, and exactly one worker process must exist. Confirm the single worker, remove only those exact stale PIDs on task restart (parents exit without reaping node children), and confirm fresh passes resume; the start mutex serializes with one-shot runs, which never take ownership. Watch mode additionally owns its singleton role with a nonce-fenced heartbeat file: a verified live owner is never stolen no matter the heartbeat age (bounded passes outlast freshness windows), takeover needs a dead/foreign process or a heartbeat past the takeover window, claims resolve by write-then-reread nonce comparison, every status publish and every mutation re-verifies first, and losers step down silently without clobbering status — because the task mutex lives in the parent shell and restarts orphan the node child.

Diagnose in order: live `/status` backend `ready` on the current generation; both frontends initialized; fresh ready adapter-health subscription for the affected handle; native `thread/read` (metadata only) + paged `thread/turns/list` for the handle via the check channel; Paseo agent `idle` with no active turn or pending permissions; recovery status `active` with `failed == 0`. A recovered backend reload (e.g. account switch) re-runs this chain automatically: Paseo resumes its threads, the fresh adapter subscribes, and the worker verifies — confirm the new generation's subscription before declaring the refresh fixed. Watch-worker durability (verified 2026-10-05): the `PaseoCodexHistoryRecovery` logon trigger repeats every 10 minutes indefinitely, so a dead/clean-exited worker is re-elected within minutes without stopping any daemon — a live nonce-fenced owner is never stolen and spare starters exit silently. Inspector `readiness` reports green only with fresh recovery status and exactly one worker; `catalogHealthy` stays separately true.

## Paged history transport

Monolithic `thread/read` with `includeTurns:true` on a large original chat (seen: 190 turns, thousands of items) risks oversized payloads on the shared path. The Paseo adapter (`shared-stdio-transport.mjs`) intercepts that request and reconstructs the response from `thread/read` with `includeTurns:false` plus `thread/turns/list` pages (`limit: 10`, `itemsView: full`, `sortDirection: asc`) with cursor-overlap validation, preserving ascending turn order. Verification (`history-utils.mjs`) and recovery use the same paged shape. Every paged read carries a real budget: the absolute restore deadline starts before initialize and covers every resume and paged read, bounded by the overall reconnect deadline (a socket opening past it never starts a restore; `open()` refuses it); live reads get ~120s, catch-up retries ~30s, at most 500 pages and 128MB (`SHARED_HISTORY_MAX_BYTES`, UTF-8 bytes) per read — the reviewed bound covering the ~95MB selected original chat — and the remaining time flows into each RPC deadline — a stall surfaces as a timeout, never a hang, and no new restore step begins on expiry. During reconnect, paged history reads (`thread/turns/list`, `thread/items/list`, `thread/timeline/list`) are buffered and retried like other read-only RPCs; model-turn and lifecycle RPCs are reported once and never replayed. If one subscribed thread's history cannot be re-read during reconnect, that thread is recorded as an incomplete history (per-chat, in-memory; aggregate pending/exhausted counts in the heartbeat) without blocking reconnect for the connection's other chats, and retried on the live connection up to 5 times at 15s intervals. The worker and inspector report an unresolved gap as pending, never healthy. The installed timeline merges adjacent same-turn text rows by concatenation and reconciles a completion against buffered streamed text — so a delta lost to an outage would corrupt the visible text if post-gap deltas were forwarded. The bridge therefore mirrors per-item streamed prefixes: on a gap it synthesizes the authoritative missing segment from the saved snapshot exactly once, then withholds ambiguous post-gap deltas until the authoritative completion reconciles the exact remainder (reasoning streams share the principle; withholding clears on item/turn completion and unsubscribe). Proven end-to-end through the installed timeline store with a lost middle delta, reasoning gaps, and terminal replays. From the moment a catch-up fails, the whole thread freezes (including not-yet-seen item IDs) so no ambiguous suffix reaches the store before authoritative reconciliation; completions still flow against the safe prefix, and a contradictory snapshot records an integrity gap with bounded retry instead of clearing silently. Replay suppression after a live retry is scoped to an active recovery flush only, so later live deltas are never dropped. These bounds reduce payload and memory pressure but do not by themselves explain a native `memory_allocation_failed` crash: treat that code as aggregate failure evidence and keep investigating scope if crashes recur.

## History comparison rules

`checkHistory` pages the full native turn list and the full Paseo canonical timeline (bounded, gap/overlap-checked; never a newest-tail sample). Text messages verify by normalized content hash; merged renderings count separately. Async question cards verify by substantive native content — question titles and option labels — because Paseo keys cards by transient call IDs that are routing metadata, not user-visible text. A card whose content is absent stays unverified and fails the check; empty substance never verifies. Counts, hashes, and card totals are the evidence; transcripts never leave the local verification.

## Async-question resolution sync

Root cause: native history carries no canonical link between an async question item and its answer — questions live as `agentMessage` items with `delivery: 'async'` and no resolution field (verified live across all loaded async items), answers as ordinary user messages, and dismissals send nothing native at all. Each frontend tracks pending questions in its own local map, so a question answered in Desktop stays pending in Paseo (and symmetrically), and re-submitting launches a second model turn.

Paseo-side repair has two halves. (1) Provider patch (`install-question-sync.mjs`, same anchor/backup/marker discipline as the catalog hook, `paseo-codex-questions-v1`): exact-format answers (`Answers to your questions:` plus exact titles) resolve ONE uniquely matching pending record with the same timeline plus permission_resolved event pair a local answer emits — live with redelivery dedup, chronological native proof when a question item arrives after its answer (ordering, never title memory), and across history resync by sweeping saved records against persisted answers anchored on exact native item/call identity (narrow unique-text fallback only). Ambiguous repeats, duplicate titles inside one card, partial answers, free text, and unrelated messages (even title mentions) never resolve; already-resolved submits acknowledge idempotently without steering. The patch activates only after the Paseo daemon reloads the provider module: reload exclusively through the guarded idle path (never during an active reply), with `question-sync-status.json` recording install state, helper build, and `pendingRollout` (cleared only by runtime provider acknowledgment, never by markers), plus `question-rollout.json` for the queued guarded idle reload; the watcher loop reinstalls (never fatally) so Paseo updates re-apply or fail loudly without touching files. (2) Transport duplicate-answer guard (`shared-stdio-transport.mjs`): exact-format `turn/steer` and `turn/start` submissions for titles already answered after their latest ask are refused with a reload-directing error instead of launching a second turn; ask/answer positions track per-item order (same-turn answers count); simultaneous submits serialize per thread with in-flight tracking released on completion, definite rejection, loss, turn end, and unsubscribe; ambiguous state falls back to one bounded authoritative check that fails closed with an actionable error rather than forwarding a possibly-duplicate turn; a re-asked identical question unblocks its new answer by ordering. True cross-client simultaneity has no adapter-side atomic primitive and stays a documented residual. Reconnect-during-submit ambiguity is contained by never replaying submits; a retry after a reported failure re-evaluates against current history.

Limits, stated plainly: remote dismissals have no protocol signal and cannot sync; Paseo answering does not clear Desktop-side cards (Desktop internals, unpatchable from here); UI rendering of resolved cards was verified at event and shape level, not by a live two-composer test.
